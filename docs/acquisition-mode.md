# Acquisition suspend and resume

Implemented and verified on the live EVK on 14 October 2026. Run as root:

```sh
cd /root/rf-watchkeeper
python3 acquisition_control.py suspend
python3 acquisition_control.py status
python3 acquisition_control.py resume
```

Suspend saves enabled/running states in `data/acquisition-suspended.json`, installs persistent systemd guards, disables automatic acquisition units, stops their timers first and then their services. Discovery includes installed and loaded `rf-watchkeeper*`, `meteor-*` and `satellite-*` services/timers, including legacy capture/preflight units. It covers the primary V4 scheduler (Tower, ATIS, AIS, FM/reference jobs), secondary sensors/433 scheduler, standalone receiver/AIS services, satellite planning/dispatch/processing/recovery/registration, health recovery, ATIS ASR/shadow/validation, interpreter and Tower anomaly workers. Future differently named launchers must be integrated before enabling them; the current systemd inventory had no other RF launchers. Automatic creation of new managed passes is stopped with the dispatcher/planner.

Dashboard, METEOR cleanup and daily audio cleanup services/timers are explicitly excluded. Data, databases, receiver configuration, logs and retained recordings are preserved. The dashboard polls `/api/acquisition` and displays **RF Watchkeeper suspended** while the marker exists. Historical RF readings remain accessible. Saved-audio actions are still operator initiated; suspend covers automatic RF/processing services, not arbitrary commands launched outside systemd.

Each affected unit receives `/etc/systemd/system/<unit>.d/90-acquisition-suspend.conf` with `ConditionPathExists=!/root/rf-watchkeeper/data/acquisition-suspended.json`. Thus dependency or manual systemd starts are skipped while suspended, including health recovery trying to restore a scheduler. Guards remain after resume, with their condition satisfied. Enablement changes persist across boot. Resume restores only saved enabled states, running continuous services and active timers; idle one-shot captures are not replayed. Disabled sensors/AIS services remain disabled if that was the preceding state. An interrupted resume retains `data/acquisition-resume-pending.json` for retry; the previous state is also archived in `data/acquisition-last-resume.json`. Calls are serialized, idempotent and errors are surfaced; retry the same command after resolving an OS error.

Installation on another EVK: place `acquisition_control.py` beside the application, install the audio units as described in [retention configuration](../config/examples/audio-retention-policy.md), and inspect its actual launcher inventory. Suspension guards are generated by the first suspend command. The mechanism assumes the deployed root path and root privileges.

Live checks: two complete cycles, repeated suspend/resume, no active acquisition units or receiver/inference processes while suspended, attempted scheduler/health/dispatch starts rejected by guards after daemon reload, dashboard available, both cleanup timers active, audio timer restart and real cleanup service successful while suspended. Previous enablement and continuous service state restored. **Current acquisition is enabled.** Reboot and a later unattended daily cycle were not tested; no disruptive reboot was needed.

Rollback: resume first while the manager is present. Disable/stop `rf-watchkeeper-audio-retention.timer`, restore backed-up application files/units, remove only generated `90-acquisition-suspend.conf` drop-ins, reload systemd, and restore saved service states. Do not erase the suspension marker before using its saved states. Deleted audio cannot be recovered by rolling back code. Private backups and state evidence are under `backups/retention-suspend-20261014/`. See [completion evidence](evidence/retention-suspend-20261014/completion.md).
